## 4. СИНХРОНИЗАЦИЯ (Sync Module v2 — `sync.js`)

### Принципы
- `pendingQueue` — офлайн-очередь append-only (**flights, transfers, actlog** — actlog добавлен 10.06.2026, раньше офлайн-действия аудита терялись) с подтверждением доставки
- `tombstones` — удалённые вылеты не возвращаются при поллинге
- `_sv` версионирование — last-write-wins для stock/squads
- `pollCloud()` каждые 30с (дельта `read_since`); `syncPullOnLogin()` каждые 5 мин (полная тихая). **Для роли viewer 30-секундный поллинг НЕ запускается** (`startPolling` проверяет `syncReadOnly()`) — только полная раз в 5 мин + одно полное обновление при входе; экономия квоты Apps Script (10.06.2026)
- `saveLocal()` — debounce 2с → `syncPushAll(true)`

### Точки записи в облако
| Данные | Стратегия | Функция |
|---|---|---|
| flights | append-only + tombstones | `syncAddFlight` |
| transfers | append-only | `syncAddTransfer` |
| stock/squads | last-write-wins по `_sv` | `syncPushStockSquads` |
| actlog | append-only + pendingQueue | `appendToCloud` |

Серверные `action`: `append_one`, `write` (полный/частичный — пропускает `undefined` листы), `read`, `read_since`, `create_user`/`update_user`, `update_ammo`. **Точечного `update_one`/`delete_one` нет** — обновить/удалить одну запись flights можно только перезаписью листа.

### Защита от потери данных (04.06.2026)
- **`syncPushAll` НЕРАЗРУШАЮЩИЙ и пишет ТОЛЬКО `{flights,transfers}`** — перед `write` подтягивает облако (`action:'read'`) и **доливает** flights/transfers, которых нет локально (merge по `id`, исключая tombstones). Итог: снимок = (локальное) ∪ (облачное) − (удалённое). Полный write больше не стирает чужие записи, ещё не полученные поллингом. Если чтение не удалось — деградация к прежнему поведению (append-записи всё равно дублирует pendingQueue). Локальные правки/удаления при этом **propagate** на ближайшем ambient-write (локальная версия пишется поверх; tombstone-записи в локали нет → удаляются из облака). **`stock`/`squads` из `syncPushAll` ИСКЛЮЧЕНЫ (09.06.2026)** — раньше ambient-write писал их с устаревшим `_sv` из объектов `state` и откатывал версию (см. блок «Дефекты A/B» ниже).
- **tombstones покрывают и удалённые loss-передачи** — `syncDeleteFlight` и `returnLossDrone` заносят `id` удалённых loss-передач в `tombstones` (паттерн `removeLoss`), иначе merge вернул бы их из облака. Фильтрация tombstone-передач: `pollCloud`, `syncPullAll`, merge в `syncPushAll`.
- **stock/squads версионируются при КАЖДОЙ правке** — `adminEditStock`/`adminDeleteStock`/`adminEditSquadPilot`/`adminEditSquadDrone`/`adminDeleteSquad`/`adminAddSquad`/`squadEditPilot` вызывают `syncBumpStockVersion()`+`syncPushStockSquads()`. Иначе `_stockVersion` оставался старым и поллинг затирал правку (last-write-wins).
- **`syncPullOnLogin`** (обе ветки) заменяет stock/squads из облака **только если `remoteStockVersion > _stockVersion`**, затем синхронизирует `_stockVersion`. pendingQueue хранит лишь flights/transfers/actlog → «нет pending» ≠ «склад выгружен».
- **Правка вылета делает обычный `saveLocal()` (Дефект C, 10.06.2026)** — `syncEditFlight`, `adminEditLossDrone`, `adminEditReturned` раньше использовали `saveLocalQuiet()`: правка ждала ambient-write, и плановый `syncPullOnLogin` (5 мин) успевал **откатить её** полной заменой flights облачной версией (включая флаг `_lossWritten` → повторное списание борта другим устройством). Теперь правка уходит debounce-write'ом — `syncPushAll` неразрушающий, обоснование Risk 3 для quiet-сохранения устарело. **Удаление** (`syncDeleteFlight`) по-прежнему `saveLocalQuiet()` — его защищает tombstone.
- **tombstones: формат `[{id,ts}]` + чистка >90 дней (10.06.2026)** — `tombstones.prune()` при загрузке `sync.js`; `addMany(ids)` — массовое добавление одним чтением localStorage. Старый формат (массив id) мигрируется на лету с `ts=сейчас`.
- **`syncPushFlightsOnly()`** — точечный `write` ТОЛЬКО листа flights (не трогает `_sv` склада). В `pollCloud` после приёма чужой потери (`writeDroneLoss`+`_lossWritten=true`) флаг возвращается в облако → другие устройства не списывают борт повторно (Risk 4).
- **`saveLocalQuiet()`** (`app.js`) — `localStorage.setItem` + отмена отложенного `syncPushAll`.
- **Остаточный предел:** одновременная правка ОДНОГО вылета двумя админами — last-write-wins (у flights нет пофайлового `_sv`). Merge закрывает потерю при ДОБАВЛЕНИИ чужих записей, не при конфликте правок одной записи.

### Аудит синхронизации 09.06.2026 — Дефекты A/B (потеря вылетов и склада)
Risk 1–5 чинили внутренности `sync.js`, но точки добавления данных в `app.js`/`parser.js` их обходили. Закрыты два корневых дефекта:
- **Дефект A — вылеты не попадали в `pendingQueue`.** `saveQuickFlight` (`app.js`) и `confirmParsed` (`parser.js`) добавляли вылет напрямую (`state.flights.unshift(f); saveLocal()`), а `syncAddFlight()` (единственный путь с гарантией доставки) был **мёртвым кодом**. Доставка держалась только на debounce-`syncPushAll` (2с) → вылет терялся, если запись не доехала, а `syncPullOnLogin` при пустой очереди делал `state.flights = loaded.flights`. **Исправление:** обе функции (обе `async`) теперь вызывают `await syncAddFlight(f)` (unshift+saveLocal+pendingQueue+попытка отправки).
- **Дефект A (страховка) — `syncPullOnLogin`, ветка `!hasPending`:** полная замена `state.flights`/`state.transfers` допускается **только если локальный массив — подмножество облачного по `id`**. Иначе слияние (облачные ∪ локальные-только), чтобы не стереть запись, ещё не доехавшую до облака. Лог `сохранено N локальных вылетов вне облака`.
- **Дефект B — ambient `syncPushAll` откатывал версию склада.** `syncPushStockSquads` ставил свежий `_sv` только в шифруемую копию (объекты `state` хранили устаревший `_sv` из последней загрузки), а `syncPushAll` через 2с переписывал stock/squads с этим устаревшим `_sv` → гейт `remoteVersion > _stockVersion` на других устройствах **отвергал** реально более новое изменение (перемещение «исчезало»). **Исправление:** (1) `stock`/`squads` исключены из `syncPushAll` целиком — склад выгружает ТОЛЬКО `syncPushStockSquads`; (2) `syncPushStockSquads` теперь пишет актуальные `id`/`_sv` **обратно в объекты `state`**.

## 4А. ГЕОМОДУЛЬ (v0.12, ТОЛЬКО ЛОКАЛЬНО — `geo.js`)

Расчёт дистанций вылетов по координатам точек.

### КРИТИЧЕСКИ ВАЖНО
`geoDB` (`geo_points_db`) и `geoAliases` (`geo_aliases`) **НИКОГДА не уходят в облако**. Стражи: `geoStripFromSync()` в `syncPushAll`/`syncPushStockSquads`; guard в `syncAddTransfer`.

### Парсер LDK (AlpineQuest, бинарный)
`geoParseLDK(arrayBuffer)` → `{points,layers}`. Точка: тег `name` + длина(4б) + имя‑число + маркер `00 00 00 (01|02)` + `ff ff ff ff` + `00 00 00 08` + lon(int32 BE) + lat(int32 BE), ÷1e7. `geoTryPoint()` валидирует маркер. Слой — ближайший заголовок `.csv` перед точкой. Кириллица — UTF‑8 (`geoDecodeUtf8`). `geoColorKey(layerName)` — ключ цвета.

### Структуры и поиск
- `geoDB`: `[{layer,color_key,num,lat,lon}]`; `geoIndex`: `{color_key:{num:point}}` (`geoBuildIndex()` при загрузке/импорте/очистке).
- **FIRST-WINS при коллизии номеров (03.06.2026):** `geoBuildIndex` сохраняет **первое** вхождение `(color_key,num)`. Причина: слой может быть склейкой подслоёв с одним именем, переиспользующих номера 1..999; первый подслой — основной. `geoDB` в порядке файла → первое вхождение = первый подслой. Диагностика — `geoDiagDuplicates()`.
- `findGeoPoint('305 вишня')` → `{lat,lon,layer,num}` | `null`. Извлекает число+цвет, ищет слой **токенно** (`geoColorMatch`→`geoWordMatch`, норм. ё→е `geoNorm`): Левенштейн (порог `max(2,floor(min(len)/2))`), общий префикс ≥4, толерантный префикс. **Приоритет** (`geoColorScore`): точное совпадение слова цвета (0) выше фаззи. Внутри слоя — точно/ближайшее по номеру. Перед поиском подставляет алиас если `geoNorm(query)` совпал.
- `calcDistance(...)` — Haversine, км.
- `geoComputeFlight(f)` → `{range_km,distance_km}`: дальность=старт→цель; путь ×2 при возврате, ×1 при потере; промежуточная точка из примечания (`geoNoteIntermediate`).
  - **Несколько точек в `target`** («647 лиловая, 695 лиловая», разделители `,` `;` `/`) — `geoFindFarthestTarget(target,start)` (11.06.2026): каждая часть через `findGeoPoint`, для расчёта берётся **дальняя от старта** (range и distance считаются по ней); ненайденные части пропускаются, нет ни одной найденной → `null`.
  - **Правило result/returned (03.06.2026):** `result==='no' && returned==='no'` → `null`, дистанции не считаются (борт не долетел). Остальное считается. Зеркально `geoRecomputeFlights` для таких **очищает** ранее записанные дистанции.
- `geoApplyToFlight(f)` — проставляет поля при сохранении (`saveQuickFlight`, `confirmParsed`).
- **`geo_locked`** — защита посчитанных дистанций. Ставится `true` автоматически при расчёте. `geoRecomputeFlights` с `includeLocked:false` (умолч.) не трогает заблокированные — смена точки старта и новый `.ldk` их не перезаписывают. В админ-журнале значок 🔒. Кнопки: «Пересчитать незаблокированные» (`geoRecalcAllForce`) и «Сбросить все блокировки и пересчитать» (`geoRecalcAllResetLocks`, двойной confirm).
- `geoRecomputeFlights({force,pilot,includeLocked,onProgress,onDone})` — **асинхронный батчевый** (по 5, `setTimeout 10`). `_runId` отменяет предыдущий запуск. force=false → только вылеты без дистанций.
- Точка старта — `squads[].start_point` («NNN цвет»). **Смена НЕ пересчитывает старые вылеты** (`squadEditStartPoint` только сохраняет) — пересчёт существующих вручную.
- Диагностика: `geoDiag()` / `geoDiagFind(query)` / `geoDiagDist(pilot,target)` / `geoDiagNotes()` / `geoDiagDuplicates()`.

## 6. ШИФРОВАНИЕ

AES-256-GCM на клиенте, каждая запись отдельно. Ключ в `localStorage` + в ссылке (`&k=KEY`). Google видит только шифртекст. Не шифруются: `users`, `ammo_catalog`.
`cfgReencrypt()` — смена ключа: читает старым → перешифровывает новым → перезаписывает облако; ключ меняется локально **только после успешной записи**; прерывается если ни одна строка не расшифровалась. Выполнять когда другие не пишут.
**`aesEncrypt` кодирует base64 поблочно (по 32 КБ, 12.06.2026)** — прежний `btoa(String.fromCharCode(...buf))` на длинных записях (большой actlog-payload) переполнял стек аргументов spread'ом → в облако уходил битый base64, `aesDecrypt` падал на `atob` («not correctly encoded»). Короткие записи проходили — ломались только длинные. Старые записи, зашифрованные битым кодом, остаются нечитаемыми (`syncDecrypt` возвращает `null` и они молча отбрасываются `filter(Boolean)`) — повторные decrypt error по конкретным id означают именно их.

- **Резервный шаблон без API** (`vrBuildTemplate`, реальные данные — анонимизация не нужна, локально): `vrGenerate` пробует API с таймаутом 10с (`AbortController`); при отсутствии ключа/сети (`navigator.onLine`)/таймауте/ошибке — автофолбэк на шаблон с уведомлением («Сеть недоступна — сформирован шаблонный доклад»). Отдельная кнопка «Шаблонный доклад» (`vrTemplate`) — принудительно без API. Шаблон: период, список пилотов, итоги, по расчётам (`Расчёт пилота {имя}`), гео-блок (налёт/средняя/макс. дальность с пилотом и датой), **потери сгруппированы по типу борта столбиком с количеством** («- {тип} — N шт.», по убыванию), серия без потерь (по всем данным — «по настоящее время»). Пусто → «За выбранный период вылетов не зафиксировано.»

### Репортаж недели (AI, v0.17) — только admin/cmd
`reportReportage` (`reports.js`, блок `// ===== РЕПОРТАЖ НЕДЕЛИ =====`) — шутливо-ироничный спортивный репортаж о достижениях пилотов через Claude API (`claude-sonnet-4-6`, `max_tokens:1000`, ключ `localStorage['anthropicKey']`; запрошенный `claude-sonnet-4-20250514` устарел/снимается 15.06.2026 — взят актуальный ID как в парсере/устном докладе). **Тип отчёта `reportage`**, опция `#repTypeReportage` показывается только для admin/cmd (`rpgIsPrivileged()`, переключение в `repToggleReportageOption()` из `fillReportFilters`); рендер и генерация гейтятся ролью. **Данные НЕ сохраняются и НЕ уходят в Google Sheets.**
- **Период** — **последний ЗАВЕРШЁННЫЙ календарный** (`rpgPeriodRange`), в отличие от скользящих окон устного доклада: неделя пн–вс (берётся предыдущая завершённая; **в понедельник — позапрошлая**, т.к. прошлая закончилась лишь вчера в вс) или месяц (предыдущий, не текущий).
- **Дельта медалей/щитов за период** (`rpgSnapshotAt(asOfMs,pilots)`): снимок «до начала» (срез на день раньше) и «конец периода», разница = получено/утрачено. Переиспользует штатный движок `calcPilotMedals`/`computeAbsoluteRecords` — **временно подменяет `state.flights` (вылеты ≤ даты среза) и `Date.now` (movable «сегодня» для скользящих окон медалей)** в `try/finally`; функции синхронны и только читают, глобальные кэши (`window._absRecords`/`_pilotMedals`) не затрагиваются. `computeAbsoluteRecords` без зависимости от «сейчас» — достаточно фильтра вылетов; медали зависят от «сейчас» лишь через `medalIsoDaysAgo`→`Date.now()`.
- **Анонимизация — только имена пилотов** (`vrIndexMap(...,'Пилот','')` → «Пилот N»), обратная замена `rpgDeanon` (regex терпим к склонениям/ё-е). Точки/НП в payload не отправляются (анонимны по построению); названия моделей бортов в payload не включаются. Payload (`rpgBuildPayload`): агрегаты по пилотам (вылеты/выполнено/потери/лучший день/дальность), дельта медалей (`MEDALS[id].icon+name`) и щитов (`ABS_RECORDS`, «🛡️ золотой щит»).
- **UI**: `rpgGenerate` (таймаут 20с, индикатор/блокировка), редактируемая `textarea`, кнопка **«📋 Копировать для Telegram»** (`rpgCopyTelegram` → «✓ Скопировано!» на 2с, plain text с эмодзи). Без API-фолбэка (только онлайн): нет ключа/сети/ошибка → статус-сообщение. Состояние — `window._rpg*`. В конец сгенерированного текста автоматически добавляется ссылка на справку о медалях (`medals.html`, 10.06.2026). Идея «визитки достижений» (текстовый блок щитов/медалей перед репортажем) пробовалась 10.06.2026 и откачена — выглядела уныло.

**Журнал вылетов:** табличный, быстрая форма, автонумерация по пилоту/дню, 10-мин окно редактирования (только кто подал; смена «вернул↔потерян» в окне пересчитывает склад и дистанции — 10.06.2026). Порядок столбцов: Дата→Время→#→Пилот→Точка→Боеприпас→БПЛА→Задача→Борт→Примечание.

### Редактирование вылетов администратором (пересчёт склада, v0.12, 03.06.2026)
Точка входа `adminEditFlight(idx,field,val)`. Для `drone`/`returned` в вылете-потере — перехват с диалогом; прочее — `syncEditFlight`.
- **Смена борта в вылете-потере** (`returned==='no'`, борт изменился) → `adminEditLossDrone` → `confirmLossDroneChange`. Да: старый борт +1 пилоту, новый −1 (фантом `qty:-1` не создаём), `updateLossTransferDrone`, `syncBumpStockVersion`. Нет: меняется только `f.drone`. `_lossWritten` НЕ проверяется (у исторических не выставлен).
- **Смена статуса «вернул↔потерян»** (`returned` yes↔no, борт указан) → `adminEditReturned` → `confirmReturnedChange`. Да yes→no: `writeDroneLoss(...)`, `_lossWritten=true`. Да no→yes: `returnLossDrone(f)` (трёхуровневый поиск как в `syncDeleteFlight`), `_lossWritten=false`. Нет: только статус. Без борта — обычная правка.
- **Флаг `_lossWritten`:** облачный поллинг (`sync.js`, `returned==='no' && !_lossWritten`) списывает потерю при приёме; флаг не даёт списать повторно.

### Медали пилотов (Обзор → Расчёты, v0.13; правила 03.06.2026)
Бейджи рядом с именем пилота (`renderDashboard`→`dashSquads`). Только локально. Блок `// ===== МЕДАЛИ ПИЛОТОВ =====` в `app.js`, стили `.medal-*`.
- `MEDALS` — каталог `id→{icon,name,color}` (9 медалей). `calcPilotMedals(pilot)` — заработанные, окно 10 дней (`medalIsoDaysAgo(9)`); без гео (`range_km`) медали 🚀/🎯 не выдаются. `computeMedalWinners()` — сравнительные. `medalsHtml(pilot)` (кэш `window._pilotMedals`), `showMedalModal(pilot,idx)`.
- **Движок присуждения** (`reports.js`, общий с отчётом): `_nomWinner`+`nomRatioTop` (числовой: 2-й < лучший×0.9), `nomPctTop` (≥10 п.п.), `nomStreakTop` (серия: разница ≥2). Один кандидат → всегда; ничья → нет.
- **Единоличные** (правило 10%): 🚀 longshot (рекорд `range_km`, нужно гео), ⚡ workhorse (макс. вылетов/10дн), 🥇 sniper (макс. % yes, **мин.5** — ужесточено с 3 10.06.2026), 🛡️ thrifty (мин. % потерь, **мин.5**), 📈 progress (рост к прошл. неделе, мин.+3), 🌟 bestday (рекорд/день, ≥2). В отчётном блоке «Отличившиеся за период» (`perfNominationLines`) порог остался мин.3 — там период произвольный и может быть коротким.
- **Верхний ярус** (инверт. 10%): 💎 veteran (макс. за всё время; все у кого `count≥max×0.9`; `w.veteran` — карта `{пилот:desc}`).
- **Абсолютные** (несколько носителей): 🔥 streak (серия без потерь ≥5), 🎯 raid (вылет `range_km>20` за 10дн).

### Абсолютные рекорды — золотые щиты (v0.15, 07.06.2026)
Отдельная система ПОВЕРХ медалей: рекорды **за всё время** по **правилу 1%**. Блок `// ===== АБСОЛЮТНЫЕ РЕКОРДЫ =====` в `app.js`, стили `.gold-*`. **Не хранятся в localStorage** — `computeAbsoluteRecords()` пересчитывается при каждом `renderDashboard()` (кэш `window._absRecords` только для модалки).
- `ABS_RECORDS` — каталог `id→{icon,name}` (те же эмодзи, 7 номинаций): 🚀 longshot (дальнейший одиночный `range_km`), ⚡ workhorse (макс. вылетов за неделю — скользящее окно 7 дней `maxFlightsInWeek`), 🌟 bestday (макс./день), 🥇 sniper (лучший % yes, **мин.20 вылетов**), 🛡️ thrifty (мин. % потерь, **мин.20**), 🔥 streak (самая длинная серия без потерь за всё время — хронологически, `returned==='no'` обнуляет, **мин.5**), 💎 veteran (макс. всего вылетов). Щит 🔥 (рекорд за всё время) показывается рядом с именем; медаль 🔥 (текущая серия ≥5) — внизу карточки.
- **Правило 1%** (`_absWinner(cands,higherBetter,mode)`): держатель — только если результат **строго >1%** относительно 2-го (`mode:'ratio'` — число ×1.01/×0.99; `mode:'pct'` — >1 процентного пункта для %). Приблизились в пределах 1% / ничья → щит исчезает у всех; 0/1 активный пилот → присуждается всегда. Снайпер/Бережливый — флайт-доля done/total (мин.20 вылетов; «активные дни» учтены тем, что делим по вылетам, а не по календарю).
- Отображение (`goldShieldsHtml(pilot,{inline})`, `pilotGoldShields`, `showAbsRecordModal`): (1) рядом с именем в карточке расчёта — **только** золотые щиты (`{inline}`, высота под заглавные буквы); (2) внизу карточки (`.crew-achievements`) — **только** обычные медали (щиты у имени не дублируются); (3) в topbar при роли `pilot_N` (`switchRole`) — золотые щиты рядом с именем; у самой учётки пилота бейдж затем перезаписывается логином в `applyRoleFromAuth` — щиты добавляются и туда (11.06.2026, раньше их видел только админ во «взгляде пилота»). Щит = эмодзи поверх золотого щита `#FFD700` (CSS `clip-path`, размер через `font-size`). **В отчётах золотые щиты НЕ отображаются.**

### «ОТЛИЧИВШИЕСЯ ЗА ПЕРИОД» (Подробный отчёт, 03.06.2026)

## 11. ДОГОВОРЁННОСТИ И ПРАВИЛА

### Код
- Файлы синхронно; перед правкой проверять баланс скобок; локальный тест — `file://`
- Глобали модуля живут в его файле (geoDB — `geo.js`; pendingQueue/_stockVersion — `sync.js`); общие (`state`,`cfg`,`authToken`,`ammoCatalog`,`actLog`) и init — в `app.js`. Модули не обращаются к глобалям `app.js` на верхнем уровне (только в рантайме — иначе TDZ, app.js грузится последним)
- **Любые пользовательские/облачные данные в `innerHTML` — через `esc()`** (имена пилотов/бортов, примечания, ammo, логины, `_src` парсера, значения `value="…"` и `<option>`). Данные приходят от других устройств и AI-парсера → без `esc` это XSS и порча верстки. Для аргументов в inline-`onclick` — дополнительно `.replace(/'/g,"\\'")`.
- **Даты-границы — локальные, через `localISO(d)`**, не `toISOString().slice(0,10)` (UTC сдвигает день; критично для «сегодня»/«за неделю»/окна медалей в UTC+3)
- **НЕ дублировать атрибут `style` в HTML** — браузер молча игнорирует второй атрибут. Так `display:none` на `#usersCard` не работал, и карточку пользователей видели все роли (инцидент 10.06.2026). Скрытие по умолчанию писать в ТОТ ЖЕ атрибут: `style="...;display:none"`

### Синхронизация
- `syncPushStockSquads()` — **никогда** не передавать flights/transfers; `writeAll` пропускает undefined; `saveLocal()` → debounce 2с
- **Любая** правка stock/squads → `syncBumpStockVersion()`+`syncPushStockSquads()` (иначе поллинг затрёт — last-write-wins по `_sv`)
- Облако заменяет локальные stock/squads только при `remoteStockVersion > _stockVersion` (stock/squads НЕ в pendingQueue)
- Правка вылета — `saveLocal()` (debounce → неразрушающий merge-write, иначе плановый pull откатит правку — Дефект C); удаление — `saveLocalQuiet()`+tombstone; см. §4

### Пилоты/борта/данные
- Список пилотов фиксированный; диалог пилота без «Ввести вручную», борта — с; борт проверяется среди бортов конкретного пилота; потерянный борт удалять полностью; при потере drone обязателен
- Нули не отображаются; отрицательные — красным
- Ред. вылета админом НЕ повторяет списание при правке прочих полей. **Исключение:** смена борта в вылете-потере и «вернул↔потерян» — пересчёт через диалог (§8)
